# Bug hunt — 2026-10-05

Reproduced against the current app (Django test client + Vitest). Each item was unguarded, missing a test, or both. Rankings are 1–5.

| Scale | 1 | 5 |
| --- | --- | --- |
| Severity | annoyance | account takeover, public address leak, or irreversible delete |
| Likelihood | needs a rare chain | happens on the normal path |
| Effort | one guard + a test | several subsystems |

## 1. Anonymous callers receive event addresses

**Severity 4** — street address (and lat/long, when set) of community events is in the public JSON. The event page copy says location is shown after sign-in, and the detail screen hides the location block for guests. The calendar cards render `event.location` with no auth check, and `GET /api/community/events/` returns it anyway.

**Likelihood 5** — every logged-out calendar load.

**Effort 2** — gate `location`, `latitude`, and `longitude` the same way `_gated` already blanks `whatsapp_link` in `_event_list_out` (`backend/community/_events.py`) and `_event_out` (`backend/community/_event_helpers.py`). Add a test next to `test_events_strips_private_fields_for_anonymous`, which currently creates events with `location=""`.

Reproduced: anonymous `GET /api/community/events/` returned `location: "18 Willow House, back door"` while `whatsapp_link` was blank.

## 2. Paused and archived tokens still pass optional JWT

**Severity 4** — `GatedJWTAuth` blocks paused, archived, and password-reset accounts. `OptionalJWTAuth` (`backend/community/_shared.py`) only checks the JWT signature. Event read, comments, and reactions use optional auth, so a paused member with an RSVP still gets the WhatsApp link and the guest list, and can post a comment. An archived user who still has `manage_events` can delete other people's comments. `GET /api/notifications/` correctly returns 403 for the same token.

**Likelihood 3** — this is what pause and archive are for. The token stays valid for the access lifetime (15 minutes), and finding 3 extends that.

**Effort 3** — when optional auth resolves a real user, run the same account-state checks and treat a blocked user as anonymous on reads and reject writes. Cover pause, archive, and `needs_password_reset` on `GET /events/{id}/` and `POST/DELETE .../comments/`. `backend/tests/test_auth_gate.py` only hits gated routes.

Reproduced: after `is_paused=True`, notifications were 403 and event detail was 200 with the WhatsApp link and the caller's guest row. `POST .../comments/` returned 201. After `archived_at` was set on a `manage_events` user, `DELETE .../comments/{id}/` returned 204.

## 3. Refresh and logout ignore account state; a stolen refresh can set the password

**Severity 5** — `POST /api/auth/refresh/` (`backend/users/_auth.py`) loads the user id from the cookie and mints a new pair. It does not check pause, archive, or `needs_password_reset`. Logout only clears the cookie. There is no denylist (`NINJA_JWT` sets lifetimes only: access 15 minutes, refresh 30 days). `complete-onboarding` is on the pending-user allowlist, so a refresh cookie copied before a reset can mint an access token and set a new password after `set_unusable_password()`.

**Likelihood 2** — the refresh cookie is HttpOnly, so this needs a copied cookie (shared computer, malware), not a normal XSS read. Once that cookie exists, the reset flow hands the holder the password.

**Effort 3** — reject blocked users in `refresh_token`. On logout, pause, archive, and password invalidation, bump a per-user session version stored in the token and checked on refresh. Add tests that pause-then-refresh and reset-then-complete-onboarding fail for the old cookie.

Reproduced: login, logout, `GET /api/auth/me/` with the old access token was still 200. After pause, `POST /api/auth/refresh/` with the original cookie was 200 twice (the first refresh does not kill the old refresh). After `needs_password_reset` plus an unusable password, that same cookie refreshed and `POST /api/auth/complete-onboarding/` set a new password (`Zxqv!m9kLp2w` verified with `check_password`).

## 4. API login never sets `last_login`, so hard delete is wrong

**Severity 4** — `hard_delete_user` refuses only when `last_login` is set, and the comment says a never-logged-in user cannot have comments (`author` is `on_delete=PROTECT`). `POST /api/auth/login/` and magic login call `authenticate` and mint a JWT. They never call Django's `login()`, so `last_login` stays null for everyone who uses the API. Admins can permanently delete active members. If that member has a comment, the delete raises `ProtectedError` (500) instead of a 400.

**Likelihood 3** — any hard delete of someone who has signed in through the app.

**Effort 2** — set `last_login` on password login and magic login. Catch `ProtectedError` and return a validation error. The hard-delete tests set `last_login` by hand, so they never notice the API path.

Reproduced: `POST /api/auth/login/` left `last_login` null. Hard delete of that user returned 204. The same flow with one `EventComment` raised `ProtectedError`.

## 5. Tentative users can search the member roster

**Severity 3** — directory and profile call `_require_member`. `GET /api/auth/users/search/` (`backend/users/_management.py`) does not. A signed-in non-member who has finished password and consent setup gets names (and phone numbers when `show_phone` is on). Search is capped at 10 rows, so this is lookup, not a full dump.

**Likelihood 3** — tentative approval is a real state. The directory UI 403s; the search API does not.

**Effort 1** — call `_require_member` (or require `is_member`) and add the case missing from `test_tentative_member_access.py`.

Reproduced: tentative user `GET /api/auth/users/directory/` was 403 and `GET /api/auth/users/search/?q=Visible` was 200 with the member's id.

## 6. Calendar feed token keeps working after pause

**Severity 3** — `GET /api/community/calendar/feed/?token=` loads the user by `calendar_token` and builds the ICS with `is_authed=True` (locations and links). Pause and archive do not clear the token.

**Likelihood 3** — anyone who subscribed before a pause keeps the URL. Calendar apps poll it.

**Effort 1** — 403 when the user is paused or archived, and clear `calendar_token` on archive.

Reproduced: paused user, feed status 200, body contained `18 Willow House`.

## 7. Archived non-member RSVP tokens still resolve

**Severity 3** — `NonMemberRsvpToken.resolve_user` checks expiry and revocation, not `archived_at`. `GET /api/community/public/my-rsvps/?token=` then returns that person's phone, email, and RSVPs. Magic login already rejects archived users.

**Likelihood 2** — needs a token issued before archive.

**Effort 1** — return None from `resolve_user` when `user.archived_at` is set. `test_public_rsvp_archived.py` only covers a new submit.

Reproduced: token issued, user archived, manage-RSVP list was 200 and included the phone number.

## 8. Removing non-members does not promote the waitlist, and blocks unpublish

**Severity 3** — `guard_or_remove_ineligible_non_members` sets those RSVPs to `REMOVED` and does not call `promote_from_waitlist`. The following capacity check only promotes when `max_attendees` grew. Waitlisted members stay waitlisted on a spot that just opened. `REMOVED` rows still count for unpublish (`_unpublish_event` uses any RSVP outside the host crew) and for `guest_rsvp_count`. The host cannot return the event to draft.

**Likelihood 3** — official event with a public RSVP and a waitlist, then the host changes the type to community with `force`.

**Effort 2** — promote inside the same transaction after the removal, and exclude `REMOVED` from the unpublish guard and guest count (the check-in report already excludes them).

Reproduced: cap 1, non-member attending, member waitlisted, `PATCH` `event_type=community` `force=true`. Non-member became `removed`. Member stayed `waitlisted`. A follow-up `PATCH` `status=draft` returned 400 `event.has_rsvps`.

## 9. Lowering `max_attendees` leaves the event overbooked

**Severity 3** — `_promote_if_capacity_increased` handles growth only. A host can set the cap below the current attending headcount. Existing `ATTENDING` rows stay. New RSVPs waitlist against a cap the event already exceeds.

**Likelihood 3** — a normal host edit on a live capped event. `test_no_promotion_on_max_attendees_decrease` only checks that the waitlisted user stays waitlisted.

**Effort 2** — reject the patch, or demote the newest attendees to the waitlist until headcount fits. Pick one and test `attending_count <= max_attendees`.

Reproduced: two attending, `PATCH max_attendees=1` returned 200, headcount stayed 2.

## 10. Turning off plus-ones leaves the extra seats occupied

**Severity 2** — headcount uses the stored `has_plus_one` flag. `PATCH allow_plus_ones=false` does not clear existing flags. New writes force the flag off, but the old row still counts as two until that person edits their RSVP. The event can look full.

**Likelihood 2** — host disables plus-ones after someone already brought one, while the cap is tight.

**Effort 2** — when the flag flips off, set `has_plus_one=false` on that event's RSVPs and promote anyone the freed seats can take.

Reproduced: cap 2, one attending row with `has_plus_one=true`, flag turned off, flag stayed true, headcount stayed 2, the next member's RSVP came back `waitlisted`.

## 11. Admin attendance-mark ignores capacity

**Severity 2** — `mark_attendance` `update_or_create`s `ATTENDING` with no cap check and no `select_for_update`. Fine for backfilling a past night. On a future capped event it overbooks. Tests use uncapped or legacy events.

**Likelihood 2** — needs `manage_users`, and only matters when the event is still in the future and capped.

**Effort 2** — if the event is upcoming and `max_attendees` is set, refuse or waitlist the extras.

Reproduced: cap 1 with one attending row, mark two other users, headcount became 3, response 200.

## 12. Magic-login `redirect` is an open redirect

**Severity 4** — `LoginScreen` sends `redirect` through `safeRedirect`, which rejects `//host`. `MagicLoginScreen` does `navigate(decodeURIComponent(redirect))`. React Router's browser history `push` calls `pushState` with that path. A scheme-relative path throws `SecurityError` (cross-origin). The catch calls `location.assign` with the same string, which navigates off the site after the token has been consumed and the user is signed in.

**Likelihood 2** — the emailed link has no `redirect` param. Someone has to get the user to open a magic-login URL with `?redirect=//…` added.

**Effort 1** — pass the param through `safeRedirect` before `navigate`. There is no test with `?redirect=`.

Reproduced: `createBrowserHistory().push({ pathname: '//evil.example/phish', ... })` called `location.assign('//evil.example/phish')`. `safeRedirect('//evil.example/phish')` would have returned `/calendar`. A memory-router run of `MagicLoginScreen` reached `navigate` with the decoded redirect and then failed route matching.

## 13. Event edit form keeps the previous event when the id changes

**Severity 4** — `EventForm` initializes `values` and RSVP questions with `useState(() => existing ? ...)`. `EventEditScreen` does not set `key={event.id}`. React Router reuses the screen when only `:id` changes, so a save can PATCH event B with event A's fields.

**Likelihood 2** — two edit URLs in one session (another event's edit link, or back/forward) without a full remount.

**Effort 1** — `<EventForm key={existing.id} existing={existing} />`. No test covers a prop change.

Reproduced: render `EventForm` with title `alpha picnic`, rerender the same instance with `beta potluck`, the title input was still `alpha picnic`.

## Checked, not filed

- Date-only `?date=` on the calendar. `date-fns` 4 `parseISO('2024-10-05')` is local midnight in `America/Los_Angeles` and `America/New_York`, not the previous day.
- Unpaid waitlist promotion is covered on purpose (`test_waitlist_payment_notifications.py`): the seat is `ATTENDING` and payment is checked on the next write.
- `request-login-link` `delivery: email|cooldown` is a documented anti-enumeration tradeoff.
- `GET /whatsapp-link/` for every signed-in member matches "members can see the group link."
- Member RSVP races at capacity already lock the event row (`test_rsvp_capacity_race.py`).
- `dangerouslySetInnerHTML` goes through DOMPurify in `HtmlContent`.

## Suggested order

1. Gate location on the public event payload (finding 1).
2. One account-state check shared by optional JWT, refresh, logout, and the calendar feed (findings 2, 3, 6).
3. Set `last_login` on API login before anyone hard-deletes from the members screen (finding 4).
4. `safeRedirect` on magic login, and `key={event.id}` on the edit form (findings 12 and 13).
5. Promote after non-member removal, and decide whether a lower cap demotes or is rejected (findings 8 and 9).
